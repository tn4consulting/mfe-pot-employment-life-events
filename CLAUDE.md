# mfe-pot-employment-life-events

## What this is

The **client-centric "you lost your job" guided journey** frontend for the mfe-pot Government of Canada MFE proof-of-technology — the app that stitches `mfe-pot-job-bank`, `mfe-pot-employment-insurance`, and `mfe-pot-dashboard` together into one narrative, rather than presenting them as separate benefit programs. Federated as a remote into `mfe-pot-shell`. Also embeds dashboard's payment-history widget directly (the one proven cross-remote widget-composition case in this architecture, not a routed remote). The fifth and final app extracted from the platform repo.

**This repo doesn't carry its own architecture doc.** Full rationale — bilingual/WCAG/GCDS requirements, the Native Federation setup, the federation-sharing policy, security model, i18n mechanism, hosting/Helm pattern, and every non-obvious gotcha behind the code in this repo — lives in **`../mfe-pot-platform/CLAUDE.md`**. Read it before making any architectural change here; this file only covers what's specific to this repo. See `../CLAUDE.md` (the `mfe-pot` meta repo) for the full 6-repo map.

## What's in this repo

- `apps/employment-life-events` — the only app; frontend-only, federated on port `4202` in local dev. No co-located BFF — there's no distinct bounded context here that justifies its own backend.
- `libs/feature-guided-journey` — the real component/business logic, including where the cross-remote payment-history widget gets mounted.
- `charts/employment-life-events` — depends only on the platform repo's `mfe-frontend-lib` (no BFF, so `mfe-backend-lib` isn't used), same shape as shell's chart.

Depends on published packages from GitHub Packages: `@tn4consulting/shared-auth`, `shared-content-client`, `shared-federation-config`, `shared-federation-runtime`, `shared-i18n`, `shared-runtime-config` (pinned in `package.json`; keep in sync with `platform-versions.json` in `mfe-pot-platform`). **Deliberately does not depend on `@gcds-core/components`/`components-angular`** — confirmed genuinely unused (only `MscaAppFrame` in `shared-ui-gcds` needs the GCDS packages) and dropped rather than carried as dead weight.

## Repo-specific things worth knowing

- **`src/runtime-config.ts` and `public/env.js` were added specifically for `ContentClient`'s `strapiBaseUrl`** — this app previously had neither (no BFF of its own, nothing to configure), but now fetches a CMS-driven intro block (`employment-life-events.intro` key) the same way `mfe-pot-dashboard`/`mfe-pot-job-bank`/`mfe-pot-employment-insurance` do. `App` (`apps/employment-life-events/src/app/app.ts`) renders it above `feature-guided-journey`, re-fetched on cross-remote locale change. `charts/employment-life-events/values.yaml`'s `frontend.runtimeConfig.strapiBaseUrl` points at `mfe-pot-platform`'s `charts/strapi` (`http://cms.mfe-pot.local`, browser-to-server, not in-cluster Service DNS).
- **A real, pre-existing production bug, found and fixed while wiring up the CMS content above**: `feature-guided-journey`'s own component used to import `TranslocoPipe` directly from `@tn4consulting/shared-i18n` for its `journey.paymentsHeading`/`journey.widgetUnavailable` chrome text, *in addition to* `App`'s own import of the same package for `auth.signInRequired`. That's two separate Nx compilation units (this app, and this lib) both importing `shared-i18n` directly, and esbuild/Vite's federation-aware chunking bundled them as two independent copies with mismatched `InjectionToken` identities — confirmed live (`kind`, real browser via Playwright, mock session, *before any of this session's other changes*) as `NG0201: No provider found for InjectionToken TRANSLOCO_TRANSPILER`, alongside an `NG0912` component-ID collision warning naming a duplicated `TranslocoLoaderComponent`. The whole page crashed blank for any signed-in citizen — not a corner case, the entire happy path. Same root-cause class as the native-federation "a plain library must never import it directly" gotcha in the platform repo's CLAUDE.md, same fix shape: `feature-guided-journey` no longer imports `shared-i18n` at all — `App` resolves `journey.paymentsHeading`/`journey.widgetUnavailable` itself (it already needs the pipe for `auth.signInRequired`) and passes them down as plain `@Input()` strings. Verified fixed the same way the bug was found: live on `kind`, real browser, no console errors, full text renders. If any *other* feature lib in this family ever imports `TranslocoPipe`/`TranslocoService` directly (grep for it under `libs/`) while its owning app also does, expect the same crash — `@jsverse/transloco` is not on the federation `shared` singleton list (see the platform repo's federation-sharing policy), so nothing dedupes the two copies automatically.
- **`PAYMENT_HISTORY_WIDGET_LOADER` (from `@tn4consulting/shared-federation-runtime`) is injected in `libs/feature-guided-journey/src/lib/employment-life-events-feature-guided-journey/employment-life-events-feature-guided-journey.ts`** — this is the DI-token pattern the platform repo's CLAUDE.md describes ("Cross-remote widget composition is host-mediated, not remote-to-remote"): the shell loads dashboard's `./PaymentHistoryWidget` and `./RemoteProviders` and hands the resolved component + providers down through this token. This app never imports dashboard directly, federated or otherwise — a plain nested `loadRemoteModule` call from here would hang forever with no error, per that same explanation. If this stops working, check the shell repo's wiring (`app.routes.ts`) before assuming the bug is here.
- **`tsconfig.app.json` had two stale references from before this token moved into `shared-federation-runtime`** (leftover paths pointing at the pre-extraction in-monorepo locations) — already cleaned up during extraction; if you see a build error referencing a `libs/employment-life-events/*` or `libs/shared/remote-registry` path that doesn't exist in this repo, that's the same class of stale-reference bug reappearing, not a new one.
- **CI** (`.github/workflows/ci.yml`): lint/test/build, then builds the image, spins up an ephemeral `kind` cluster, `helm install`s this chart, and curls the Ingress-routed hostname to confirm it serves. See `README.md` for local install/serve/build/Docker/Helm instructions.
