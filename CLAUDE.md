# mfe-pot-employment-life-events-mfe

## What this is

The **client-centric "you lost your job" guided journey** frontend for the mfe-pot Government of Canada MFE proof-of-technology — the app that stitches `mfe-pot-job-bank-mfe`, `mfe-pot-employment-insurance-mfe`, and `mfe-pot-dashboard-mfe` together into one narrative, rather than presenting them as separate benefit programs. Federated as a remote into `mfe-pot-msca-shell`. Also embeds dashboard's payment-history widget directly (host-mediated via `mfe-pot-msca-shell` — see the platform repo's CLAUDE.md "Federation" section). The fifth and final app extracted from the platform repo, and the second converted to React.

**This repo doesn't carry its own architecture doc.** Full rationale — bilingual/WCAG/SCDS requirements, the Native Federation setup, the federation-sharing policy, security model, i18n mechanism, hosting/Helm pattern, and every non-obvious gotcha behind the code in this repo — lives in **`../mfe-pot-platform/CLAUDE.md`**. Read it before making any architectural change here; this file only covers what's specific to this repo. See `../CLAUDE.md` (the `mfe-pot` meta repo) for the full 7-repo map.

## What's in this repo

- `apps/employment-life-events-mfe` — the only app; frontend-only, federated on port `4202` in local dev. No co-located BFF — there's no distinct bounded context here that justifies its own backend. Repo directory, Nx project, federation identity (`federation.config.mjs`'s `name`), Docker image, and Helm chart/release are all named `employment-life-events-mfe` — the `-mfe` suffix disambiguates this internal federated remote from either host app's own front-door name (see the meta repo's `../CLAUDE.md`). The underlying business-domain naming (Nx `scope:employment-life-events` tag, CMS content keys) deliberately stays un-suffixed — that's domain identity, not hosting identity. `apps/employment-life-events-mfe/src/app/*.tsx` holds every component directly — no separate `libs/<name>/feature-*` library the way this repo had before converting to React (see the platform repo's CLAUDE.md, "Components live in the app"). `App.tsx` renders `GuidedJourney.tsx`, which composes the guided-journey checklist: `StaticChecklistSection.tsx` (self-reported items with no owning app's data behind them — departure/administrative steps, CV/training, benefits awareness), `JobSearchChecklistItem.tsx`/`EiChecklistItems.tsx` (items with real completion signals, see below), and `checklist-data.ts` (the static bilingual copy for the former — same "no upstream owner, stays local" pattern as `mfe-pot-dashboard-mfe`'s `ConsiderThisList.tsx`).
- `charts/employment-life-events-mfe` — depends only on the platform repo's `mfe-frontend-lib` (no BFF, so `mfe-backend-lib` isn't used), same shape as either shell's chart.

Depends on published packages from GitHub Packages: `@tn4consulting/shared-auth`, `shared-content-client`, `shared-federation-config`, `shared-federation-runtime`, `shared-i18n`, `shared-locale-sync`, `shared-runtime-config`, `shared-ui-scds-core` (pinned in `package.json`; keep in sync with `platform-versions.json` in `mfe-pot-platform`). **No longer scds-core-free**: this app used to deliberately skip it (confirmed genuinely unused at the time — no `scds-*` element of its own, unstyled beyond the embedded `PaymentHistoryWidget`) but now renders the guided-journey checklist's `scds-checklist`/`scds-checklist-item` elements directly (see `GuidedJourney.tsx`, `StaticChecklistSection.tsx`), the same way job-bank/dashboard/employment-insurance already did — `register-scds.ts` (imported once, from `App.tsx`) and `scds-elements.d.ts` follow those apps' own established pattern exactly. `shared-federation-config` was bumped from a stale `^0.6.0` pin to `^0.7.0` alongside this change — 0.6.0 predates `sharedUiScdsCoreFederationDependency` existing at all, so a lower pin fails the federation build outright once this app tries to share the SCDS singleton.

## Repo-specific things worth knowing

- **`src/runtime-config.ts` and `public/env.js` were added specifically for `ContentClient`'s `strapiBaseUrl`** — this app previously had neither (no BFF of its own, nothing to configure), but now fetches a CMS-driven intro block (`employment-life-events.intro` key) the same way `mfe-pot-dashboard-mfe`/`mfe-pot-job-bank-mfe`/`mfe-pot-employment-insurance-mfe` do. `App.tsx` renders it above `GuidedJourney.tsx`, re-fetched via a `useEffect` on cross-remote locale change. `charts/employment-life-events-mfe/values.yaml`'s `frontend.runtimeConfig.strapiBaseUrl` points at `mfe-pot-platform`'s `charts/strapi` (`http://cms.mfe-pot.local`, browser-to-server, not in-cluster Service DNS).
- **`federation.config.mjs`'s `exposes` map (`./Component`) must point at `apps/employment-life-events-mfe/...`, not the pre-rename `apps/employment-life-events/...`** — confirmed this is exactly the gotcha the platform repo's CLAUDE.md documents ("`federation.config.mjs`'s `exposes` map needs checking on any app that exposes something beyond its own root component") — a stale path here fails the federation build with `FsPath ... does not exist`.
- **A real, pre-existing production bug found while this app was still Angular, fixed as part of wiring up the CMS content above**: the old `feature-guided-journey` lib imported `TranslocoPipe` directly for its own chrome text, in addition to `App`'s own import of the same package — two separate compilation units both importing Transloco tripped a real `NG0201`/`NG0912` crash (confirmed live, whole page blank for any signed-in citizen). Fixed at the time by having the feature component take its translated strings as plain `@Input()`s from `App` instead of importing Transloco itself. **This bug class doesn't exist anymore, and won't recur** — now that this app is React, `GuidedJourney.tsx` and `App.tsx` share the exact same `useTranslations()` hook call site conceptually (props passed down, same as the Angular-era fix), and React has no per-bundle DI-singleton-identity concept for two compilation units' imports to collide over in the first place. Kept here as a one-line historical note, not active guidance.
- **`usePaymentHistoryWidgetLoader()`/`useJobApplicationsWidgetLoader()`/`useEiReportingStatusWidgetLoader()` (all from `@tn4consulting/shared-federation-runtime`) are called in `GuidedJourney.tsx`/`JobSearchChecklistItem.tsx`/`EiChecklistItems.tsx`** — this is the host-mediated widget-composition pattern the platform repo's CLAUDE.md describes ("Cross-remote widget composition is host-mediated, not remote-to-remote"): `mfe-pot-msca-shell` loads dashboard's `./PaymentHistoryWidget`, job-bank's `./JobApplicationsWidget`, and employment-insurance's `./EiReportingStatusWidget`, handing each resolved component down through its own Context. This app never imports any of the three directly, federated or otherwise — a plain nested `loadRemoteModule` call from here would hang forever with no error. If any of these stop working, check `mfe-pot-msca-shell`'s wiring (`apps/msca-shell/src/app/routes.tsx`, `EmploymentLifeEventsRoute`) before assuming the bug is here — and specifically check whether that repo's own `build.mjs`/`serve.mjs` correctly marks `@tn4consulting/shared-federation-runtime` as `external` in its non-federation-managed entry bundle, a real bug found and fixed once (see `mfe-pot-msca-shell`'s own CLAUDE.md and commit history) that silently degrades a widget to its "unavailable" fallback with no console error.
- **The job-search and EI checklist items derive real completion state, not a self-reported guess** — `JobSearchChecklistItem.tsx` passes an `onApplicationsLoaded` callback prop into job-bank's mounted `JobApplicationsList` (added to that component in `mfe-pot-job-bank-mfe` specifically for this — optional, additive, doesn't affect that app's own zero-prop usage of it), and `EiChecklistItems.tsx` passes `onStatusLoaded` into employment-insurance's `ReportingStatus` (same pattern, added in `mfe-pot-employment-insurance-mfe`). Both widgets mount as soon as their loader resolves — not gated behind the "complete" check — specifically so their own fetch effect runs and the callback fires; only their visual detail is hidden (via inline `display: none`, not unmounted) until there's something real to show. If a checklist item never flips to "complete" even though the citizen genuinely has an application/claim, suspect this callback wiring or the widget-loader Context (previous bullet) before assuming the checklist's own logic is wrong.
- **The checklist itself renders as `scds-checklist`/`scds-checklist-item`** (`@tn4consulting/shared-ui-scds-core`, defined in `mfe-pot-platform`'s `libs/shared/ui-scds-core`) — a presentational-only pair with no completion state of its own (`complete`/`complete-label` are caller-controlled props, same shape as `scds-badge`'s `tone`); the interactive control inside each item (a native checkbox for self-reported items, a `scds-link` that becomes a status link once complete) is slotted in as plain children. Added specifically for this checklist — no other app in the family had a "list of rows with a leading complete/incomplete marker" component before.
- **The shell route this app is reached through is `/job-loss`, not `/employment-life-events`** — a deliberate rename in `mfe-pot-msca-shell`'s `routes.tsx`/`AppFrame.tsx` (URL/nav-link only; this repo's own federation identity, directory name, and Nx project stay `employment-life-events-mfe`, since that's domain identity, not hosting identity — see the meta repo's `../CLAUDE.md` naming-convention section). `mfe-pot-platform`'s `apps/mfe-e2e` specs were updated to match.
- **CI** (`.github/workflows/ci.yml`): lint/test/build, then builds the image, spins up an ephemeral `kind` cluster, `helm install`s this chart, and curls the Ingress-routed hostname to confirm it serves. See `README.md` for local install/serve/build/Docker/Helm instructions.

## Renovate

`renovate.json` extends `github>tn4consulting/mfe-pot-platform` — the shared preset (groups `react`, `react-dom`, and `@tn4consulting/shared-ui-scds-core` into one coordinated pinned bump, the federation-shared singletons — now including this repo, per the note above). Don't hand-roll React/SCDS version bumps here independently of the other repos; `platform-versions.json` in `mfe-pot-platform` is the source of truth for what version they should all be on.
